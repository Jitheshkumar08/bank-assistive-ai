WorkflowState architecture — bank-ai language engine

Who builds what, who calls what, and who reads or changes workflow_state. Every edge comes from a line in the source, as of 2026-11-09. Click a box or an arrow to see the evidence.

What the source shows (verified)

  1. The pipeline and DomainWorkflowRunner never touch. voice_pipeline.py doesn't mention DomainWorkflowRunner. The runner is built and driven only by service/domain_runtime.py (L183, called at L269–L381), which is the College domain runtime.
  2. Only ConversationManager writes workflow_state (conversation/manager.py L31 and L105). Everything else reads it or calls one of ConversationManager's transition methods.
  3. VoiceAssistantPipeline reads the state but never changes it. It uses NEEDS_NEW_INTENT_STATES (L29–33, L385) to pick a route. Every workflow change goes through DialogueManager.
  4. WorkflowLoader doesn't depend on any of the other five. It imports only json and pathlib. Its only link to the state is that it shares callers with it.
  5. Two engines drive one state machine. DialogueManager (banking) and DomainWorkflowRunner (college) each read the state and call the same transitions, with separate guard logic.
  6. complete_workflow() and load_workflow() have no guards. complete_workflow() (L253–255) sets COMPLETED from any state, and load_workflow() (L170–190) sets ACTIVE from any state. suspend, resume and cancel do check the current state.
  7. restore_paused_workflow() (L379) is never called outside tests. DialogueManager stashes a snapshot at dialogue/manager.py L2251, but outside debugging/ no code restores it.
  8. No import cycles. An AST import graph of app/ and service/ found none. state.py is a leaf: it imports only enum and typing.
